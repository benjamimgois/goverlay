# centralized-tools-logging Specification

## Purpose

Ensures complete, centralized, and reliable diagnostic logging for all tools managed by GOverlay, facilitating troubleshooting across all supported game sessions.

## Requirements

### Requirement: Centralized tool log synchronization
The system SHALL discover and synchronize any existing log files generated by game tools (including `optiscaler.log`, `dlss-enabler.log`, `fakenvapi.log`, `helixsr.log`, `helixsr_loader.log`, `nvexec.log`, `afmf.log`, `vksumi.log`, `vkbasalt.log`, `reshade.log`, `mako.log`, `lsfg.log`, and `bgmod-uninstaller.log`) from the game directory or its tool subdirectories (such as `HelixSR/`) into the central logging directory `~/.local/share/goverlay/logs/<GameDirName>/`, while `bgmod` itself SHALL NOT create or maintain active log files within the game directory.

#### Scenario: Case-insensitive OptiScaler log synchronization
- **WHEN** OptiScaler writes `optiscaler.log` or `OptiScaler.log` in the game directory during game execution
- **THEN** the system discovers the file regardless of casing and synchronizes its full content into `~/.local/share/goverlay/logs/<GameDirName>/optiscaler.log`.

#### Scenario: DLSS Enabler and FakeNVAPI log synchronization
- **WHEN** DLSS Enabler writes `dlss-enabler.log` or `fakenvapi.log` in the game directory
- **THEN** the system synchronizes those files into `~/.local/share/goverlay/logs/<GameDirName>/dlss-enabler.log` and `~/.local/share/goverlay/logs/<GameDirName>/fakenvapi.log`.

#### Scenario: bgmod-uninstaller log synchronization
- **WHEN** `bgmod-uninstaller` runs in the game directory or is triggered via GOverlay
- **THEN** `bgmod-uninstaller.log` is recorded in `~/.local/share/goverlay/logs/<GameDirName>/bgmod-uninstaller.log` and `/tmp/bgmod-uninstaller.log` without creating `bgmod-uninstaller.log` in the game directory.

#### Scenario: HelixSR log synchronization from root and subfolders
- **WHEN** HelixSR writes `helixsr.log`, `helixsr_loader.log`, or `nvexec.log` in `<GameDir>` or `<GameDir>/HelixSR/`
- **THEN** the system discovers the files and synchronizes them into `~/.local/share/goverlay/logs/<GameDirName>/helixsr.log`, `helixsr_loader.log`, and `nvexec.log`.

#### Scenario: AFMF log synchronization
- **WHEN** AFMF writes `afmf.log` in the game directory
- **THEN** the system synchronizes the file into `~/.local/share/goverlay/logs/<GameDirName>/afmf.log`.

### Requirement: MangoHud diagnostic logging
The system SHALL capture MangoHud diagnostic messages from the game execution process and store them in `mangohud.log` exclusively in the central log directory `~/.local/share/goverlay/logs/<GameDirName>/mangohud.log`, leaving the game directory free of log files.

#### Scenario: MangoHud diagnostic output capture
- **WHEN** a game is launched with MangoHud enabled
- **THEN** diagnostic, initialization, and error messages from MangoHud are captured and written to `~/.local/share/goverlay/logs/<GameDirName>/mangohud.log`, and no `mangohud.log` file is created in `<GameDir>`.

### Requirement: Game directory log elimination
The `bgmod` wrapper and associated utilities SHALL NOT create `bgmod.log` or any tool log files directly inside the game executable directory (`<GameDir>`). All launcher and tool diagnostic messages SHALL be directed to `/tmp/` and the central logging directory `~/.local/share/goverlay/logs/<GameDirName>/`.

#### Scenario: Launcher execution without game directory pollution
- **WHEN** a game is launched via `bgmod`
- **THEN** `bgmod.log` is written to `/tmp/bgmod.log` and `~/.local/share/goverlay/logs/<GameDirName>/bgmod.log`, and no `bgmod.log` file is created in `<GameDir>`.

#### Scenario: Subprocess stderr tool logging without game directory log descriptors
- **WHEN** `RunSubprocessLogger` captures tool diagnostics (such as MAKO, lsfg-vk, OptiScaler, vkSumi, vkBasalt, MangoHud, or DLSS Enabler) from standard error
- **THEN** log lines are written exclusively to descriptors in `CentralLogDir`, and no corresponding log file descriptors are opened or written in `<GameDir>`.

### Requirement: GOverlay UI log viewer tab integration
The GOverlay user interface SHALL open the corresponding log file for the currently active tool tab and sub-option selection (including OptiScaler, DLSS Enabler, HelixSR, MangoHud, vkBasalt, vkSumi, MAKO, lsfg-vk, AFMF, and ReShade).

#### Scenario: Opening DLSS Enabler log from Upscaler tab
- **WHEN** the user has DLSS Enabler selected in the Upscaler tab and clicks "Open Log File"
- **THEN** the interface opens `~/.local/share/goverlay/logs/<GameDirName>/dlss-enabler.log`.

#### Scenario: Opening MangoHud log from MangoHud tabs
- **WHEN** the user is on any MangoHud configuration tab and clicks "Open Log File"
- **THEN** the interface opens `~/.local/share/goverlay/logs/<GameDirName>/mangohud.log` if it exists, falling back to `bgmod.log` if uninitialized.

#### Scenario: Opening HelixSR log from Upscaler tab
- **WHEN** the user has HelixSR selected in the Upscaler tab and opens the active tab log
- **THEN** the interface resolves `~/.local/share/goverlay/logs/<GameDirName>/helixsr.log`.

#### Scenario: Opening AFMF log from Frame Interpolation tab
- **WHEN** the user has AFMF selected in the Frame Interpolation tab and opens the active tab log
- **THEN** the interface resolves `~/.local/share/goverlay/logs/<GameDirName>/afmf.log`.

#### Scenario: Opening ReShade log from ReShade tab
- **WHEN** the user is on the ReShade tab and opens the active tab log
- **THEN** the interface resolves `~/.local/share/goverlay/logs/<GameDirName>/reshade.log`.

### Requirement: Clean process lifecycle and subprocess supervision
The `bgmod` launcher SHALL supervise the execution lifecycle of game processes without circular process dependencies, ensuring that background logging processes terminate cleanly upon game exit and do not prevent external supervisors (such as Steam's reaper) from detecting game completion.

#### Scenario: Clean game exit on Steam with active tool logging
- **WHEN** a game is launched via `bgmod` under Steam with one or more diagnostic tool logs enabled
- **AND** the user closes the game normally
- **THEN** the game process tree terminates, `bgmod` detects child process exit, `RunSubprocessLogger` terminates cleanly, and Steam transitions the game status from running to stopped without manual user intervention.

#### Scenario: Forwarding cancellation signals to supervised game process
- **WHEN** Steam or an external launcher sends a termination signal (SIGTERM or SIGINT) to `bgmod`
- **THEN** `bgmod` forwards the signal to the child game process, waits for process tree teardown, signals the logger, and exits cleanly.

### Requirement: Isolated stream redirection and pipe closure
The `bgmod` launcher SHALL ensure that the write descriptor of the tool logging pipe is owned exclusively by the game process tree and closed in the supervisor process, guaranteeing that closing the game triggers an end-of-file (EOF) on the logger read descriptor.

#### Scenario: Pipe write end closed in supervisor
- **WHEN** `bgmod` spawns the game process with standard error redirected to the logging pipe
- **THEN** the supervisor process immediately closes its inherited write descriptor and restores its original standard error stream, ensuring that no lingering write references keep the pipe open after the game exits.

### Requirement: Per-game MangoHud benchmark CSV directory and auto-organization
The system SHALL configure the default MangoHud benchmark `output_folder` to `~/.local/share/goverlay/logs/<GameDirName>/` for active game profiles (or `~/.local/share/goverlay/logs/` in Global mode), ensure the target directory exists on disk, upgrade legacy `~/.local/share/goverlay` paths on profile load, and organize loose `<app>_YYYY-MM-DD_HH-MM-SS*.csv` benchmark files into `~/.local/share/goverlay/logs/<app>/`.

#### Scenario: Default MangoHud output_folder for a selected game profile
- **WHEN** the user selects a game profile (or resets MangoHud defaults while a game is active) and saves the configuration
- **THEN** `output_folder` in the game's `MangoHud.conf` points to `~/.local/share/goverlay/logs/<GameDirName>/` and the directory is created on disk if it does not already exist.

#### Scenario: Upgrading legacy root output_folder path
- **WHEN** an existing `MangoHud.conf` specifies the legacy default `output_folder=/home/<user>/.local/share/goverlay`
- **THEN** loading the profile upgrades `logfolderEdit` to `~/.local/share/goverlay/logs/<GameDirName>/` (for a game profile) or `~/.local/share/goverlay/logs/` (for the Global profile).

#### Scenario: Auto-organizing loose MangoHud CSV logs into game subdirectories
- **WHEN** loose MangoHud benchmark files such as `pascube_2026-10-17_14-07-18.csv` and `pascube_2026-10-17_14-07-18_summary.csv` exist directly in `~/.local/share/goverlay/` or `~/.local/share/goverlay/logs/`
- **THEN** GOverlay moves both files into `~/.local/share/goverlay/logs/pascube/` so they appear under the `pascube` game entry in GPLOT.

### Requirement: Sensitive launch argument redaction in diagnostic logs
The `bgmod` wrapper SHALL detect and redact sensitive arguments (including authentication passwords, login tokens, exchange codes, and account IDs) before writing launch arguments to `/tmp/bgmod.log` and central log files.

#### Scenario: Epic Games launch with exchange code and auth password
- **WHEN** a game is launched with parameters containing `-AUTH_PASSWORD=<secret>` or `-epicuserid=<id>`
- **THEN** `bgmod` logs the argument with the sensitive value replaced by `[REDACTED]` (e.g. `Arg X: -AUTH_PASSWORD=[REDACTED]`), ensuring plaintext credentials are not written to `/tmp/bgmod.log` or central log files.

#### Scenario: General parameters preserved intact
- **WHEN** a game is launched with standard non-sensitive flags and paths (such as `-dx12`, `-novid`, `-high`, or executable paths)
- **THEN** `bgmod` logs these arguments verbatim without modification.
